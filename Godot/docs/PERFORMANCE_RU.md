# Как измерять производительность

Цель 60 FPS означает бюджет кадра 16,67 мс; это целевой бюджет, а не измеренный результат. Пока не выбран/протестирован конкретный CPU/GPU, обещать FPS нельзя. Программный llvmpipe использовался только для проверки рендера.

1. Начать с Medium, 1920×1080, одинакового маршрута/позиции/времени суток. Для измерения выключить V-Sync/лимит, включить F2; для игры затем вернуть ограничение.
2. Измерить CPU/GPU, memory, draw calls, primitives и physics в Godot Debugger → Monitors / Profiler. Отдельно записать старт, границу чанка, разрушение досок, вход в рюкзак и загрузку слота.
3. Сравнить Low / Medium / High. Low: render scale .85, без MSAA/SSAO/volume fog, тени до 45 м, меньше травы. Medium: native scale, MSAA2, тени 80 м, без SSAO/volume fog. High: MSAA4, SSAO, volume fog, тени 110 м и больше травы. High не гарантирует лучший FPS.
4. Тестировать экспортированную сборку на целевой машине; редактор, software renderer и --fixed-fps проверки не являются игровым benchmark.
5. Зафиксировать GPU/CPU/RAM/драйвер/Godot, разрешение/пресет, средний FPS, 1% low и пики. Пройти длинный маршрут и проверить память/GC/VRAM минимум 30 минут.

Известные пределы: synchronous startup NavMesh/10-чанковый прогрев, native allocation/rebuild мешей/ConcavePolygonShape на переходе, coarse batch culling/LOD, все станции/GLB в памяти, SubViewport рюкзака добавляет проход рендера при открытии, нет floating origin или настоящей asset unload. Occlusion не обязана скрывать отдельные деревья внутри большой MultiMesh AABB. Следующие изменения должны следовать измерениям, а не обещанию «улётного FPS».
